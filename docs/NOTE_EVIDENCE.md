# Note evidence protocol

The experimental fixed vocal recipe retains model observations independently of edits. `GET /api/songs/{song_id}/notes` returns `score_sha256`, `evidence_generation` and the revision of the same score snapshot as its notes. To inspect a note from that response, call `GET /api/songs/{song_id}/notes/{note_id}/evidence` with `expected_revision`, `expected_score_sha256`, and `expected_generation`. A mismatch returns 409. All three are needed: layout and Undo can reuse a revision and identical bytes can occur on different edit branches. Evidence GET reads the current database snapshot and does not run Song reconciliation.

A `linked` response identifies one selected performed MIDI event using `selected-midi-v1:<sha256>:<midi_notes index>`, its performed seconds, interpreted grid seconds, written quarter positions, and every current locator in its tie chain. The selected layer is not the complete raw YourMT3 output. `unavailable` means the evidence or proof is missing or unsupported; `ambiguous` means multiple written chains match. Neither status is a probability or an assessment of musical accuracy. A source-audio seek is returned only when the owned WAV, source and model hashes, untrimmed context, playback duration and applicable beat receipt validate. It is a candidate from the interpreted grid, not an observed acoustic onset; unsupported or inconsistent sources return null.

For example, an owned synthetic score with one note tied across two bars may return `locators: ["p0-m0-n0", "p0-m1-n0"]`. These positional locators apply only to the returned score snapshot.

A newly ingested fixed-recipe Song receives an active baseline only after its retained evidence and original written score validate together. Existing Songs without that admission remain unavailable; matching content alone cannot establish identity. The first publication layout can retain an active baseline when its notes and clock remain unchanged. Every other score or revision write invalidates the active lineage by default, including Undo and untracked edits. The desktop includes the revision, hash and generation from `/notes` in its sparse structure PATCH. Existing clients may omit them, but a supplied stale precondition returns 409. For a proven untied pitch-only edit with revision and hash preconditions, the score and an append-only patch edge commit in the same SQLite transaction and activate its successor lineage. An edge records both revisions and XML hashes, the locator, before/after pitch and spelling, source ID, and manual-edit reason. Undo retains old edges without reactivating them. Tied pitch edits, boundary edits, merges, and independent ground truth are outside this slice.

## Verification on retained song results (2026-11-18)

Six cached results from five unique recordings (recipe v2: five; v3: one) passed normal completed-Job ingestion into isolated databases, first publication initialization, guarded API editing, normal MIDI export, and Undo. The baselines linked 3,243 selected source-event instances to 3,606 written locators. Eighteen API samples covered tied and untied links and verified grid-based audio seeks. Each case retained its source ID across one pitch edit, rejected stale GET/PATCH requests, and exported the same MIDI timing and track roles with exactly one pitch change. Undo retained the patch history and invalidated the active lineage. Original and copied inputs remained byte-identical.

This was a cached API/storage replay, not new model inference, independent ground truth, listening review, or approval of musical quality.
